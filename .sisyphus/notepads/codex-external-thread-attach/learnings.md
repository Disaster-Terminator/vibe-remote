# Learnings

- `config/v2_sessions.py` already has the repo's safe persistence-evolution pattern: add a new top-level `SessionState` field, load it with `payload.get("new_key", default)`, and emit it explicitly from `save()`.
- `get_agent_session_id()` is consumed by Codex, OpenCode, and shared session restoration code as a plain string lookup, so external Codex attachment metadata must stay out of `session_mappings`.
- Duplicate attach detection does not need to scan unrelated runtime state; a dedicated `codex_external_attachments` store is enough for reverse lookup by `codex_thread_id`.
- The new Codex attach seam can stay transport-owned by `CodexAgent` if the service depends on a cwd-scoped transport provider instead of spawning or caching transports itself.
- Workspace validation needs two layers of identity: `realpath(cwd)` catches directory moves/symlink aliasing, while a repo-root fingerprint (`repo:<root>` else `cwd:<realpath>`) gives downstream code a deterministic same-repo vs different-workspace signal.
- Keeping `read_thread()` in a service with no session facade dependency makes the preview-only guarantee easy to prove: transport dispatch happens, but persisted session mappings and external attachment records stay untouched.
- The least invasive place to thread Codex attach UX state through `/resume` is the existing `NativeResumeSession.locator`: the command layer can normalize a `locator["codex_attach"]` block with inspect metadata plus explicit `submission_payloads` for `resume` and `fork` without changing Slack/Discord/Telegram/Lark modal signatures.
- WeChat’s text fallback needs to fail closed for attach-aware Codex entries: listing them is safe, but numeric/latest shortcuts must not jump straight into `handle_resume_session_submission()` because that would skip the inspect-first + explicit-action requirement.
- The least invasive Task 3 enrichment path is to keep `NativeResumeSession` unchanged and populate attach metadata directly on the Codex provider’s `locator`, since current resume consumers only depend on the existing ID and preview fields.
- Codex native-session listing needs a synchronous wrapper around async attach-service discovery because `/resume` calls the provider from inside an already-running event loop.
- The missing piece for resumed external-thread continuity was runtime pre-registration: `CodexSessionManager` needs a pending-attach alias before `thread/resume`/`thread/fork` awaits, otherwise approvals or notifications emitted during reattach cannot be routed back to the current IM request.
- Duplicate external-thread safety can stay deterministic without scanning generic session mappings: use the persisted Codex external-attachment reverse lookup to find candidate conflicts, then gate it with `CodexSessionManager.is_session_live()` so only active writers trigger fork/reject behavior.
- Approval handoff for resumed external Codex threads fits the repo best when it reuses `QuestionUIHandler` with a dedicated callback prefix; that preserves the existing button/modal IM interaction path instead of inventing Codex-specific message plumbing.
- The safest Task 5 handler shape is to treat Codex attach as an opt-in branch off the existing `/resume` bind flow: resolve attach metadata from the selected `NativeResumeSession`, validate the workspace before routing/persistence, then persist both the ordinary mapping and the external provenance only after `thread/resume` or `thread/fork` succeeds.
- For Codex attach candidates, explicit `action_intent` should win over candidate heuristics, but duplicate-attachment safety can still force a fork when another binding already owns the same external thread id.
- The cleanest Task 7 seam is a shared `modules/im/resume_picker.py` model: adapters can render the same attach preview, validation, and explicit `submission_payloads` without re-deriving Codex policy from raw locator fields.
- Slack is the odd one out because modal submissions do not carry the original session objects; passing `working_path` through the existing resume entrypoint lets the modal rehydrate the selected native session and stay inspect-first without stuffing large attach payloads into modal metadata.
- Telegram and Feishu stay lightweight if Codex attach uses a small in-memory inspect state after the normal picker selection, instead of inventing a second top-level command or reworking the whole resume list UI.
- The remaining attach-coverage gaps were all fail-closed branches that already existed in code: partial legacy attachment-record load defaults, app-server responses with no thread payload, session-handler rejection when attach returns no resolved thread id, resume-only duplicate conflicts, stale approval callbacks, and provider-side `unverifiable` workspace metadata.
- `CommandHandlers._build_codex_attach_picker_payload()` is the narrowest stable seam for UI-payload coverage: it can prove inspect-only Codex candidates expose inspect metadata without leaking Resume/Fork submission payloads, while keeping the focused attach suites independent from platform bot imports.
- When a focused failure-path test preloads attachment state through `_StubSettingsManager.upsert_codex_external_attachment()`, the correct invariant is "no additional write happened" (stable upsert count), not "the upsert log is empty".
- The scenario harness sweet spot for Codex attach is to reuse the real `SessionHandler.handle_resume_session_submission()` with tiny test-side stubs around settings, IM delivery, native-session discovery, and Codex attach service responses; that keeps the scenario at the service boundary without pulling in full controller/runtime dependencies.
- A service-boundary continuity scenario can prove the post-attach next turn cheaply by resolving the stored `session_key + base_session_id + agent` mapping from the same IM conversation after the bind step, which matches the repo's lightweight scenario-harness philosophy better than spinning up a full backend loop.
- The OpenCode binary exposed on this host's `PATH` (`~/.local/bin/opencode`) is only a shell wrapper; the real reusable regression binary lives at `~/.opencode/bin/opencode`, so regression staging must prefer the home install path over `shutil.which('opencode')`.
- For Docker regression builds, a staged local OpenCode binary in `_tmp/three-regression/shared-home/.opencode/bin/opencode` is a more deterministic source than the unpinned `curl https://opencode.ai/install | bash` path, which depends on the GitHub latest-release API and can fail closed.
- Codex `/new`/clear semantics must clear persisted `codex_external_attachments` alongside normal Codex session mappings; otherwise later `_start_or_resume_thread()` and duplicate-attachment lookup can treat stale sidecar provenance as live state.
- The smallest correct fix for the `/resume` loop freeze is the async caller boundary in `CommandHandlers`: offload `_list_recent_native_sessions()` / `_build_resume_picker_sessions()` with `asyncio.to_thread()` so Codex attach discovery can still use the existing sync provider/service contract without blocking the main controller loop.
- A reliable regression for this bug is to stall `list_recent_sessions()` in a synchronous stub and assert an `asyncio.sleep()` still completes promptly while `handle_resume()` is awaiting the worker-thread result; that fails on the old inline implementation and passes once listing is offloaded.
- 2026-04-20: Resume confirmation preview must resolve from the final bound `effective_session_id`; Codex fork attach flows can intentionally change the target thread id after submission.
- 2026-04-20: Real Slack modal `session_select` interactions arrive as `block_actions` with `action.type == "static_select"`, so the `/resume` inspect-first modal update path has to branch there instead of waiting for `plain_text_input` dispatches.
- 2026-04-20: The shared `modules/im/resume_picker.py` presentation layer is enough to recover actionable Codex attach state during Slack rehydration if it promotes flattened provider locator fields into explicit `submission_payloads` carrying both `action_intent` and `codex_thread_id`.
