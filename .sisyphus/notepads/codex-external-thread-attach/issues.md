# Issues

- `tests/test_v2_sessions.py` intentionally round-trips a legacy nested `session_mappings` payload that does not satisfy the runtime type annotation, so the touched test needed `cast(Any, ...)` to keep Pyright diagnostics at zero without changing coverage.
- The new focused pytest file needed pytest-discoverable naming (`Test...` class and a `duplicate_lookup` test name) so the task's targeted verification commands select real tests.
- Importing `modules.agents.codex.attach_service` through the package initially triggered the full `CodexAgent` import chain and failed test collection in the base conda env because `yaml` is not installed there; switching `modules/agents/codex/__init__.py` to a lazy `CodexAgent` export fixed focused service imports without changing runtime behavior.
- `tests/test_codex_agent.py` stubs the `modules.agents.codex` package during import, so adding new Codex runtime imports (`attach_service`, `CodexPendingApproval`, `question_ui`) required the test harness to expose package `__path__` metadata and compatible stub classes before the focused `external_attach` tests could collect.
- `tests/test_resume_session.py` originally subclassed `core.controller.Controller`, which pulled in `apscheduler` during pytest collection in the base conda env; replacing that test-only dependency with a plain stub controller kept the focused resume tests runnable without changing production code.
- The base conda env used for focused pytest does not ship the optional Slack and Discord SDKs, so `tests/test_codex_attach_ui.py` had to install tiny in-process stubs before importing those adapters; that keeps the attach UI tests lightweight without changing runtime dependencies.
- The new scenario catalog YAML files trigger false-positive LSP errors because the workspace YAML schema is incorrectly bound to a CrowdSec schema; Python diagnostics are clean, but YAML LSP cannot reach zero without changing unrelated editor/schema configuration.
- `./scripts/run_three_regression.sh` cannot start in this workspace because the required local-only `.env.three-regression` file is missing; only `.env.three-regression.example` exists, and its header explicitly says the secret-filled real env file must stay local and uncommitted.
- The first binary-staging attempt copied the `PATH` shim from `~/.local/bin/opencode`, which is just a host-specific wrapper script; prioritizing `~/.opencode/bin/opencode` fixed the regression build.
- After the OpenCode-specific fix, `./scripts/run_three_regression.sh` progressed past the previous OpenCode install layer and is now blocked by an unrelated Docker registry/network error while resolving `node:20-slim` (`failed to resolve source metadata for docker.io/library/node:20-slim`).
- `core/handlers/command_handlers.py` still reports many pre-existing Pyright attribute-access errors because the controller/IM client in that file are typed as dynamic objects; this fix removed the new typing issue it introduced, but the broader baseline remains outside the scope of Review B.
- Focused pytest in the base conda env still needs `PYTHONPATH=.` because the repo is not installed into that environment; without it, collection fails on `ModuleNotFoundError` for top-level `core` and `modules` imports.
